# How Low End is built

A guide for developers. What the app does is written, one code per behaviour, in the [requirements](specs/requisiti.md) (in Italian); the README and the [user guide](user-guide.md) tell it to players. A longer description of the architecture, with diagrams of the flows at run time, is in [specs/architettura.md](specs/architettura.md).

## In one paragraph

Low End is a single-module Flutter app for Android (package `com.luigir86.low_end`). It has three sections (metronome, harmony, tuner) that share one audio engine, one microphone and one set of settings. There is no backend, no database and no network code. State lives in plain `ChangeNotifier` controllers, passed down the widget tree by one `InheritedWidget`; there is no state-management package.

## Layers

```
screens (features/*/…_screen.dart, …_panel.dart)   what you see and touch
        │ listen to
controllers (…_controller.dart, app/settings.dart)  state and rules, no Flutter widgets
        │ call, through small interfaces
outputs (audio/*_output.dart, mic_input.dart, …)   sound, microphone, notification, wakelock
        │ backed by
packages: flutter_soloud, record, audio_service, wakelock_plus, shared_preferences
```

Every outside thing sits behind an interface with a silent or fake twin (`ToneOutput`/`SilentToneOutput`, `ClickOutput`/`SilentClickOutput`, `PianoOutput`/`SilentPianoOutput`, `MicInput`/`FakeMicInput`, `AudioRoute`/`FakeAudioRoute`, `BackgroundAudio`, `ScreenAwake`/`FakeScreenAwake`, `PianoMixer`/`LocalPianoMixer`, and under the looping bars `LoopEngine`, whose fake with its own clock is in `test/fake_loop_engine.dart`). The tests use the twins, so they need neither a phone nor a sound card.

## Sound

- **One engine.** `soloud_engine.dart` starts the [SoLoud](https://solhsa.com/soloud/) engine once, on the first sound, at 48 kHz (the phones' own rate, so nothing is resampled on the way out), and lets that sound wait 300 ms while the phone's output ramps up (a click right at the start came out as a double "tra-ta"). A limiter on the whole mix (no drive, ceiling −0.3 dB) keeps the sections from ever clipping together.
- **Light with the sound.** A sound is heard some time after the engine mixes it: the engine's buffer, the phone's path and, over Bluetooth, the radio. `AudioRoute` (`audio_route.dart`, backed by `AudioRoute.kt`) says where the sound goes, and `outputLatencyFor` how late it is heard; the metronome's ring and the progression's chord on screen lag that much, so the light comes with the click.
- **Headphones unplugged.** `AudioRoute.kt` passes on Android's *becoming noisy* broadcast, registered for as long as the app lives (not only its screen: on Android 11 and older the back button closes the screen while the sound plays on); `PauseRules` stops what plays, `LowEndApp` shows a *Resume* notice, and the notification is left paused with its play button, as a music player does. The Xiph libraries are left out of the build (`pubspec.yaml`, `no_xiph_libs`): the clicks and the tone are made in memory, and the piano's FLAC files are decoded by miniaudio's own decoder, which does not need them.
- **Whole bars as loops.** The metronome does not fire timers. `ClickSound` renders **one bar** of clicks (a short synthesised woodblock tick, higher on the first beat; softer clicks for the subdivisions (`Subdivision.inner`: where each falls in the beat, the swung ones at 60% of the pair, as MuseScore's Swing); with the click on 2 and 4, beats 1 and 3 left silent, with what is inside them) as a PCM buffer and `BarLoopPlayer` loops it gaplessly, so the time cannot drift. Changing the tempo or time signature renders a new bar.
- **Harmony.** `PianoSound` renders the chord (or the bars of a progression) from 13 recorded notes (stereo, 48 kHz FLAC, three touches, with the dampers), pitched up and down and put right where the piano was out of tune, into a loop **of the same length** as the metronome's bar, in a small room (`Freeverb`). Only the notes a chord needs are decoded, the first time it plays. On the Harmony tab, while nothing plays, the loop a touch would start is mixed ahead (`PianoOutput.prerender`), so the touch only starts it. When the piano stops or the chord changes, a short tail (`PianoSound.tailWav`) carries on from the very sample the loop left, so the notes are let go as a pianist does instead of cut. Struck on every beat or arpeggiated, a new note or chord keeps the loop's place in the bar: the old chord plays on to the next pulse and the new one is struck on it (`BarLoopPlayer`, `onPulse`), so the pulse never stumbles; struck once a bar, or in a progression, it starts from the top. `LoopTransport` makes a second loop that starts while another plays wait for the next bar line, so chords and clicks stay together. The **walking bass** style (`WalkingBass`) writes a line for the whole loop (the root on the one, chord and scale tones, a half step or a fifth into the next chord, a fill at the end of a four-bar phrase; always the same for the same chords), played on a plucked double bass (9 notes of Meatbass, 3 touches, a few takes each, mono 48 kHz FLAC, decoded only when this style plays), and the piano comping lightly above it; it goes into the same loop, so nothing else changes. A single chord is walked over four bars.
- **Sustained tone.** `DroneSound` makes the steady, warm tone of a held note as a seamless loop; its pitch never wavers, so it is a true reference. It is what plays when the player chooses the held tone.
- **One request at a time, one clock.** The metronome and Harmony apply a change through `LatestRequest`: one at a time, and a change made meanwhile replaces the one waiting, so the sound only ever catches up with the latest choice. Both line their screen up with the sound through `SoundClock`, which knows where a loop began and the output's latency.
- **Where the mixing runs.** On Android the piano's loops and tails are mixed in an isolate that lives as long as the app and keeps the decoded notes (`IsolatePianoMixer`), so the screen never waits for a mix. The recordings themselves are read from the assets on the main isolate and moved to it (on Android an isolate's own request for an asset was never answered, and 1.4.0 waited for ever). If it cannot start, fails, or does not answer its first request within 20 s, the same mix runs on the screen's thread (`FallingBackMixer`, `LocalPianoMixer`). A web page has no such thread: there every mix runs in slices of a few milliseconds between frames (`runInSlices`), and the buffers are `Float32`.
- **The engine behind a seam.** `BarLoopPlayer` and `LoopTransport` call the engine through `LoopEngine`, the few SoLoud calls they use; `test/bar_loop_player_test.dart` follows on a fake engine with its own clock how a loop is replaced, comes in on the other's bar line, leaves its tail and fades.
- **Volume** is the phone's media volume; there is no balance control between the sections. Each section starts and stops its own sound from the middle of its dial (`MetronomeController.toggle`, `DroneController.toggle`, `TunerController.toggle`); the tabs and the swipes only navigate. A sound started while the other plays waits for its next bar line, and its controller reports the time left (`waitLeft`) and the beats left (`beatsLeft`) for the countdown in the middle of the dial. While the piano plays, a change of song, progression, style or key of a progression is a hand-over (`DroneController._handOver`, `BarLoopPlayer.beginHandOver`): the old loop fades to a third until its next bar line, the new one comes in on it; clicks meeting it (`play(atMeeting:)`) drop to a sixth at once and wait for the piano's real start (`LoopTransport.meeting`) (RF-ARM-15). The metronome keeps the tempo shown (`bpm`) apart from the tempo heard (`soundingBpm`), which follows + and − after 0.3 s of rest and TAP when the taps stop (RF-MET-08); Harmony follows `soundingBpm`.

## Tuner

`RecordMicInput` streams 16-bit PCM from the `record` package, `Pcm16Decoder` turns it into samples, and `PitchDetector` finds the fundamental with the **YIN** algorithm (28–2800 Hz, 28–700 Hz for the bass, where it rejects voices and hiss; a short period is placed by its multiples further along the curve, so high notes are as precise as low ones). `TunerController` smooths the readings, owns the listening/paused state and starts the microphone only after the first frame is drawn (`test/startup_test.dart`). Coming to the tuner starts it only when neither the metronome nor the harmony plays (`autoStartAllowed`); when it starts listening while one of them plays (a touch on its dial), `PauseRules` stops them and `LowEndApp` shows a snackbar with a *Resume* button, so the microphone hears only the instrument. Leaving the tab, opening the settings or sending the app to the background stops the microphone, and nothing resumes by itself.

## Playing with the screen off

`MediaNotificationAudio` (on `audio_service`) runs a foreground service of type `mediaPlayback` with a notification, so Android does not freeze the app. `NowPlayingNotification` (`lib/app/playback_rules.dart`) decides what it shows. The notification is there only while something plays, or after its own pause: the service leaves the foreground on pause (`androidStopForegroundOnPause`), so that it can remove the notification when the sound stops, and it is not exported, so Android 11+ keeps no "resume" card with a play button. It asks for `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `POST_NOTIFICATIONS` and `WAKE_LOCK`. `WakelockScreenAwake` keeps the screen on, optionally, while something plays or the tuner listens.

## Settings

`AppSettings` keeps language, note names, octave numbering (scientific or Italian), reference A (every hertz from 415 to 445), screen-on (on by default), circle layout, the lock on the swipes between sections, the width of the in-tune zone (2, 5 or 10 cents), the tuner's instrument and transposition, the metronome's tempo, time signature, subdivision and click on 2 and 4, the section left open, Harmony as it was left (one JSON value under `harmony`, in the words of the songs' JSON; the eight `harmony_*` keys of 1.3 are read once and removed), and the "guide seen" and "swipe hint seen" flags in `shared_preferences`, on the phone only (Android backup is off in the manifest). Unreadable settings never stop the app: it starts with the defaults.

## Look

All colours are in `lib/app/theme.dart` (bronze on ebony, always dark: one accent for the whole app), the font sizes and control shapes in `lib/app/style.dart`; `docs/style.md` is the style sheet that says what each is for, and `test/style_test.dart` keeps font sizes from being written anywhere else. The font is **Edwin** (regular and bold), with **Noto Music** supplying the ♩ that Edwin lacks; both are bundled and licensed under the SIL OFL. The launch screen colour in `android/app/src/main/res/values/colors.xml` must match the theme (`test/theme_test.dart` checks it). Note names follow the language (Do Re Mi or C D E) or the user's choice, and octave numbers are scientific (A4 = 440) or Italian (La3 = 440) independently of the names.

## Tests

`flutter test` runs everything (several hundred tests, around a minute): unit tests of the controllers, sound and pitch maths; widget tests of the screens; `accessibility_test.dart` (labels, touch targets, contrast); `startup_test.dart` (nothing heavy at launch); and `test/review/` (the layout matrix: English and Italian, the phone set to light or dark (the app stays dark), text scale up to 2×, phones down to 320×568 and landscape (915×412, 640×360, a tablet), with no overflow and the tab dots showing while something plays). The tests load Roboto and the Material icons from `test/fonts/`.

`test_screenshots/ui_review_test.dart` renders every screen to PNG for visual review and for the Play Store screenshots:

```
flutter test test_screenshots/ui_review_test.dart --update-goldens
```

CI (`.github/workflows/ci.yml`) runs three jobs side by side on every push to `main` and every pull request that touches more than texts (`*.md`, `docs/` except `docs/llm-actions.json`, `store/`): `dart format --set-exit-if-changed lib test`, `flutter analyze` and `flutter test`; a debug APK for arm64 only (the C++ audio engine compiled once; Gradle cached); the web build. A new push to a pull request cancels its previous run.

## Release

See [store/README.md](../store/README.md): `flutter build appbundle --release` for Google Play, signed with the upload key in `android/key.properties` (git-ignored). Raise the number after `+` in `pubspec.yaml` before each upload. To install on a phone, `flutter build apk --release` and `adb install -r build/app/outputs/flutter-apk/app-release.apk` keep the app's data when the signing key is the same.

## Web app

The same code builds a web app for the iPhone (`web/`, published on GitHub Pages by `.github/workflows/web.yml`). The few differences sit behind the same interfaces as the tests' fakes: `SpeakerAudioRoute` for `AndroidAudioRoute`, no media notification, `offThread` in place of `Isolate.run` and the piano mixed in slices on the page's thread in place of its isolate, Safari's audio session in `web_audio_session.dart`, the audio engine loaded after the first frame (`web_audio_engine.dart`). What it cannot do on an iPhone, such as playing with the screen locked, is in [web.md](web.md).

## No network

There is no networking code in `lib/`, the release manifest has no `INTERNET` permission and no font or file is downloaded. How this was checked is in [offline.md](offline.md). The web app is downloaded once from GitHub Pages and then kept on the phone by its service worker; it asks nothing of any other server.
